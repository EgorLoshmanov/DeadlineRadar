Проверена рабочая конфигурация после включения GigaChat. Telegram принимает токен, GigaChat возвращает проверенный результат, рабочая SQLite не содержит обнаруженных ошибок целостности. ## Дополнение: рассылка, лимиты и приоритет LLM

По запросу реализованы три оставшихся функциональных пункта:

- Публикация старостой атомарно создаёт очередь в `group_publications` для текущих участников, кроме автора. Доставка запускается при подтверждении, восстанавливается при запуске и проверяется планировщиком. Повторное подтверждение не добавляет рассылку; позднее вступление не воспроизводит публикацию. Перед запросом повторно проверяются членство, срок, сдача и настройка уведомлений.
- `users.plan` сохраняет локальный план. `free` допускает 15 созданных активных задач, `student` и `group` снимают лимит. Квота проверяется в транзакции после проверки повторного сохранения. Старые записи не удаляются при миграции или понижении плана. `/plan` показывает расход и переключает план без оплаты, сохраняя незавершённый черновик. Входящие задания других старост не учитываются; своё общее задание активно, пока нужно хотя бы одному текущему участнику.
- LLM получает каждый допустимый текст при включённой конфигурации. Защитные проверки выполняются после ответа. Исправления нескольких дат могут использовать ответ модели; неподдерживаемый пояс, неверное время, выдуманное расписание или неправильный номер вызывают резервный разбор. Общий бюджет — 2,5 секунды. Два напоминания сохранены на всех планах по конкретному ТЗ.

**267 тестов прошли** командой `python -m unittest discover -s tests -q`. Автономный `python -S run_test.py` и компиляция также прошли. Новые проверки охватывают миграцию планов, конкурентное создание последнего слота, повторное подтверждение при заполненной квоте, переключение плана без потери черновика, рассылку и индивидуальную сдачу через aiogram, восстановление очереди и немедленный триггер при длинном интервале планировщика. Дополнительно проверены выход из группы во время подготовки, отказ одному адресату, потеря подтверждения Telegram, отмена до/после начала запроса и устаревший отказ после пересоздания аккаунта.

Реальный `python main.py --check-llm` прошёл за **1,34 секунды**. Дополнительная публичная фраза «Лаба 3 по БД не до 15 октября, а до 16 октября в 18:00» дала `parsing_method=llm`, срок `2026-10-16 18:00`, предмет «Базы данных», задание «Лаба 3» за **0,934 секунды**. Рабочая БД и реальные Telegram-пользователи в этих проверках не использовались.

Новая очередь не заполняется существующими заданиями при обновлении. Неопределённый результат сетевой отправки расходует попытку без повтора; при такой аварии публикация может быть пропущена. Подтверждённый `RetryAfter` разрешает повтор после задержки. Публикация не расходует окна двух плановых напоминаний. Исходники и автоматическая миграция вступят в силу после перезапуска бота.

## Границы проверки

Групповой сценарий с двумя настоящими Telegram-аккаунтами и фактическая доставка новых уведомлений в этой проверке не выполнялись. Они проверены через настоящий диспетчер и планировщик с имитацией транспорта. Реально подтверждены доступ к Telegram API и ответы GigaChat.

Бюджет ожидания результата парсером ограничен 2,5 секунды, затем используется локальный разбор. Синхронный HTTP-запрос выполняется в отдельном потоке: отмена ожидания не останавливает поток немедленно. При задержке DNS или сети он может завершиться позже; до этого новые запросы данного клиента используют локальные правила. Завершение CLI также может ждать этот поток. Это существующее ограничение транспорта, оно не устранено изменением календарного контекста.
